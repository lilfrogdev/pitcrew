# Account-owned empty repository creation

Native accounts can create an empty Cloudflare Artifacts repository only when the operator explicitly configures both `CREATE_ACCOUNT_ACTOR` (an immutable `account:<user-id>` principal) and `CREATE_REPOSITORY_NAME` (one valid repository name). Both are absent by default. This approval limits admission; ownership always comes from the verified account/session, never a supplied actor, email, username, or namespace.

The native local client uses `GET /api/repository-creations` to discover its approved name and its own managed creation records. Other accounts cannot discover the approval or pending records. `POST /api/repositories/create` accepts exactly `{ "name": "operator-approved-name", "credentialConsent": true }`. The local relay requires the mutation nonce and same origin, captures the held account before reading the bounded body, and refuses an account change. Cloud ingress again validates origin, media type, exact body, route, and the authenticated stable principal.

Creation uses the existing durable repository lifecycle journal. It serializes name checks, checks project capacity, persists a pending intent before the single external mutation, and creates read-only with default branch `main`. It never writes initial code, creates a thread, issues an invitation, or imports/adopts an existing name. Cloudflare unavoidably returns an initial Git token; Pitcrew does not store, log, return, or use its plaintext. Cleanup checks the immutable repository ID across token metadata awaits, revokes only the sole expected initial token by ID, and verifies cleanup before ownership registration. Multiple or incomplete token records remain quarantined without revoking unrelated tokens.

The original verified session and approval are checked after namespace discovery and immediately before creating the durable intent. They are checked again under the existing authority queue before registration, after reading head metadata and rechecking the immutable repository ID. Sign-out, revoke-all, expiry, another sign-in, or changed approval cannot replace the original operation's authority. Cleanup of an already-created repository continues even after authority is lost; ownership does not. Registration uses a fresh verified profile and produces a fresh project with only that account as owner. Legacy memberships, credential provenance, other projects, and invitations are not transferred.

## Results and recovery

- `200 ready`: the exact cleaned repository is registered to its account owner, with immutable `repositoryId` and `projectId`.
- `202 pending`: provisioning is in progress or its outcome is unknown. A durable ambiguous intent is never automatically resubmitted, cleaned up by guessing a name, or adopted from a name collision. Refresh the account's status and investigate an unresolved intent.
- `202 cleanup_required`: the exact created ID is known but initial credential cleanup is incomplete. An explicit consented POST for the same approved name retries cleanup of that same resource only.
- `202 registration_required`: cleanup is ready, but account registration could not complete. An explicit POST captures a new original session and re-verifies the same known immutable repository before registration. It never creates another repository.

Requests remain idempotent across concurrent requests, lost responses, and Durable Object restarts. Already registered requests return the same IDs. Collision, retired name, source identity change, missing approval, and revoked session fail closed. The frontend never retries a creation POST automatically, treats unknown responses as status checks, and invalidates pending UI completion when the account changes.

`REPOSITORY_LIFECYCLE`, import/delete, execution, infrastructure admission, cloud conversation, and trusted publication remain independently disabled. Internal lifecycle reuse does not enable those generic routes. Empty sources retain the existing uninitialized base-SHA marker; this flow supplies no executable source or Git write credential. No AUTH_DB migration or new session/password/enrollment issuance is needed. Existing lifecycle SQL is initialized lazily.

## Rollout and costs

Roll out reviewed source and the two exact creation variables together, preserving the complete existing bindings, secrets, Access restriction, migrations, limits, and disabled paid/security gates. Refresh the local frontend/relay with the same source, preserving the frozen fixture Worker and approved runtime overlays. A local middleware restart may require the user to personally sign in again. No hosted frontend is required. Recheck the account and Artifacts name immediately before live creation; verify the actual immutable resource, sole owner, and completed token cleanup afterward. Tests exercise real Better Auth, D1, HTTP ingress, and workerd with a synthetic external Artifacts transport; they do not establish live provider integration or actual account ownership.

[Cloudflare Artifacts pricing](https://developers.cloudflare.com/artifacts/platform/pricing/) requires the existing Workers Paid plan. As checked October 8, 2026, Artifacts operations/storage billing begins October 14. The included monthly allowance is 10,000 operations and 1 GB storage; overages are $0.15 per 1,000 operations and $0.50 per GB-month. Aggregate account usage and future content determine charges. A single empty repository needs no paid inference or plan change, but remains persistent storage. Confirm the concrete source/configuration rollout and resource-specific temporary-token/storage consent before a live capability change.
