# Repository lifecycle

The Repositories workspace uses `/api/repositories` through the existing local API transport. It does not call Cloudflare directly or receive Git tokens. A local authenticated relay must forward this path to the protected cloud backend; that connection is owned by infrastructure integration and is not provided by this change.

The Worker routes lifecycle requests before initializing the execution coordinator. Every request passes the existing verified Access principal, exact owner email, audience, issuer, hostname, and mutation origin checks. `REPOSITORY_LIFECYCLE=enabled`, production mode, and the trusted `ARTIFACTS` binding are all required. The default deployment remains disabled. The infrastructure owner supplies the pinned account and `pitcrew` namespace; request bodies cannot select either.

| Route                              | Contract                                                                                                                                                                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/api/repositories?cursor=…`   | At most 50 namespace metadata entries, plus managed pending/cleanup entries on the initial page; opaque next cursor.                                                                                                        |
| POST `/api/repositories/create`    | `{name, credentialConsent:true}` creates an empty read-only repository with default branch `main`.                                                                                                                          |
| POST `/api/repositories/import`    | `{name, url, credentialConsent:true}` imports only public `https://github.com/owner/repository` URLs, default branch, depth 1, read-only. Credentials, query strings, other hosts and private integrations are unsupported. |
| POST `/api/repositories/reconcile` | `{name}` checks the immutable created resource ID and retries initial credential cleanup, never resubmitting an import/create.                                                                                              |
| POST `/api/repositories/delete`    | `{name, confirmation:name}` deletes only a managed ready repository whose immutable ID still matches.                                                                                                                       |

Names are 1–63 lowercase alphanumeric/hyphen characters, starting alphanumeric. Mutation bodies are stream-bounded to 2 KiB. New names are preflighted through at most 20 pages of 200 namespace entries, then Cloudflare's atomic creation prevents replacement. A durable metadata record prevents resubmitting the same name after retries, ambiguous transport results, or deletion. Changed operation/source retries are rejected. The registry admits at most 200 names including tombstones.

Artifacts creation/import automatically mints an initial Git token. The form explicitly discloses the credential, platform-defined scope/expiry, delayed cleanup, and possible storage usage, and requires consent. Plaintext is discarded without Git use, storage, logs, or response exposure. After a successful creation response, the Worker stores only resource ID and metadata, then obtains that exact repository and revokes the sole initial active token ID in its quarantine. Multiple token records require owner investigation; unrelated credentials are never automatically revoked. No execution/configuration admission is provided for these read-only repositories. If the repository is not ready or cleanup fails, status is `cleanup_required`; bounded manual reconciliation is available. Initial metadata failure leaves `pending` and requires owner investigation; it cannot automatically authorize token cleanup or deletion of an uncertain existing resource.

Known import errors return allowlisted actionable messages while retaining pending quarantine; no provider failure is treated as proof of absence. Protected names are rejected before credential minting. Retired names cannot be provisioned again. Listing compares immutable IDs so replaced external resources are not presented as managed.

Delete persists `deleting` intent before the namespace call. A lost response stays visible for reconciliation: exact `NOT_FOUND` confirms deletion; the original immutable ID confirms the repository still exists and restores ready status for a newly confirmed retry; all unknown failures or replacements stay protected. Tombstone delete retries are idempotent.

Create/import HTTP waits at most five seconds and returns 202 pending while the same request's `waitUntil` task continues. Worker background lifetime/platform import limits still apply; interruption can leave pending metadata or a credential requiring reconciliation. Depth 1 limits history, not repository byte size. There is no automatic retry loop, import replacement, rollback deletion, token reissuance, OAuth connection, or execution run.

Delete opens a native modal, states the exact name and irreversible repository/content/token consequences, and requires typing that case-sensitive name. Existing external repositories, `pitcrew`, `pitcrew-test`, the configured execution repository, pending imports, cleanup records, and deleted tombstones are protected server-side. Namespace deletion is performed only after a fresh immutable-ID check. Error text is allowlisted; raw service errors never reach the UI.

This initial workspace lists metadata/status only. New repositories do not automatically become Work projects or enable executions. Protected backend/Access and the local authenticated relay are required before actual lifecycle operations. The final user create/import action supplies resource-specific consent; no resources are provisioned by implementation or tests. Private imports and adopting existing repositories require a separate integration and authorization design.

Binding contract reference: https://developers.cloudflare.com/artifacts/api/workers-binding/ and the installed `@cloudflare/workers-types` generated interfaces. Generated list types currently omit the documentation's status field, so readiness is never inferred from a list response.
